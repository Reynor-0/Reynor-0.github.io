## TXE8124

TXE8124 是车载 IO Expander 芯片，通过 SPI 总线扩展 GPIO。zone controller MCU 的 GPIO 不够用，用 TXE8124 扩展出更多 IO 控制外围器件（电磁阀、传感器、指示灯等）。

### 工作模型

SPI 访问不能在中断上下文里直接做（SPI 是同步阻塞操作，中断里阻塞会导致实时性灾难）。驱动采用"中断入队 + 工作线程出队读 SPI"的异步模型：


```
TXE8124 INT 引脚中断
    │
    ▼
txe8124_int_handle()          ← 中断上下文
    │ 检查 b_async_op && scheduler_started
    │ → os_queue_send(g_txe8124_interrupt_queue, &device_index)
    ▼
txe8124_read_main_thread()    ← 工作线程，while(1)
    │ os_queue_receive(queue, OS_MAX_DELAY) 阻塞
    │ 收到 device_index → txe8124_update_port_value() → 读 SPI 刷新缓存
    ▼
SPI 总线访问
```

## 测试部门反馈的问题

### 问题描述


- **触发场景**：ECU 进入 standby（睡眠）阶段时，触发 EcuM deinit 流程恰好收到唤醒源。
- **现象**：小概率出现 TXE8124 工作线程访问 SPI 引发 trap（硬件异常/数据访问错误），设备复位。
- **特征**：偶发、难复现，只在 standby 与唤醒源时序竞争时触发。

### 定位

1. **日志分析**：trap 前最后日志是 TXE8124 中断处理 + queue send，随后工作线程被唤醒访问 SPI，trap 在 SPI 读操作。
2. **代码审查**：看 `txe8124_deinit` 原实现——只清了 `device->status = DEVICE_UNINITIALIZED` 和中断状态，**没有删除工作线程 `g_txe8124_thread_handle`**，也没清 `g_resource_init_flag`。
3. **根因确认**：deinit 后工作线程仍在 `while(1)` 阻塞在 `os_queue_receive`；standby 边界中断进来，`txe8124_int_handle` 检查 `b_async_op && scheduler_started` 仍成立（线程没删、调度器还在）→ device_index 入队 → 工作线程被唤醒 → 调用 `txe8124_update_port_value()` 读 SPI → **SPI 资源已被 deinit 释放/设备已关电** → trap。

### 分析原因

**deinit 与工作线程生命周期不同步**。deinit 只清设备状态，工作线程仍在 `while(1)` 等队列，被中断唤醒后访问已释放的 SPI → trap。

### 修复方案

**1. `txe8124_deinit` 新增删线程逻辑**
在txe8124_deinit()里，增加删除工作线程的逻辑，清除 `g_resource_init_flag`，保证不在有访问SPI的情况。

**2：`txe8124_write` 异步条件增加 NULL 检查**

deinit 置 NULL 后，后续写操作短路退出，不走异步路径访问 SPI。

**3：`txe8124_int_handle` 异步条件增加 NULL 检查**
deinit 置 NULL 后，后续中断不再往 queue 放事件。
